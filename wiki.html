01FOUNDATION2 MIN READ

What is ResolvX?

ResolvX is a Discord-first support ticket system. It is designed to give communities a structured place to receive requests, coordinate staff, preserve useful context, and review important actions.

The product starts in Discord rather than requiring every community member to learn a separate customer-support portal. Public panels provide entry points; departments and tags help route a request; forms collect details; private ticket channels host the conversation; and lifecycle controls give staff a shared way to manage the work.

↗
Current brand and command names

The product and website are branded ResolvX. The current bot source still documents slash commands beginning with /supportforge. Those names are implementation details that can change separately from the website. Use the commands actually registered by your deployed bot.

02SETUP & ADMINISTRATION5 MIN READ

Getting started safely

A sensible setup begins with the runtime and permissions, not with clicking every button that looks promising. Prepare a test guild first; production surprises are a particularly tedious kind of entertainment.

Before setup

  • A Discord application and bot. Configure the bot in the Discord Developer Portal and grant the permissions required for the exact features you plan to test.
  • A supported runtime. The current repository README lists Node.js 22.5 or newer for the documented self-hosted setup.
  • Neon PostgreSQL. The intended production persistence provider is Neon/PostgreSQL. Configure the environment variables described in the bot repository's .env.example.
  • Protected secrets. Keep tokens, database URLs, and deployment credentials in environment settings or a secrets manager. Never put them into public HTML, Git commits, screenshots, or support tickets.
  • A non-production test guild. Test permission boundaries, setup/restore, ticket creation, closing, recovery, and destructive-action confirmation before onboarding members.

First-run workflow

  1. 01
    Prepare the runtime and database

    Install the project dependencies, provide the real environment values locally or through the host, and ensure the Neon database is reachable. Do not run destructive integration tests against production data.

  2. 02
    Apply migrations and verify the build

    Follow the bot repository's documented migration, build, and test steps. A running process is not proof that migrations or interactions are healthy.

  3. 03
    Register slash commands

    Register the commands using the repository's deployment script so Discord knows which commands the bot supports. Command changes may not appear until registration has run.

  4. 04
    Run setup in the test guild

    Use /supportforge setup if that is the command registered by your deployed version. Inspect the created channels, categories, permissions, settings panel, and recovery controls.

  5. 05
    Publish a test support panel

    Create a simple department route first, then submit a test ticket as a normal member. Confirm that the ticket is private and accessible to the expected staff roles.

  6. 06
    Exercise failure paths, too

    Test unclaim, pending/resume, close/reopen, role changes, restoration, and a denied permission. Only move to production once the actual deployment behaves as expected.

03MEMBER & STAFF WORKFLOW6 MIN READ

Creating and managing a ticket

Tickets give one support request a consistent home. State names help the team tell the difference between work that is active, waiting, finished, and retained for reference.

How a member opens a request

  1. 01
    Choose the correct public panel button

    Find the server's published support panel and select the department or form that best matches the issue. If the server uses several panels, read the instructions before choosing.

  2. 02
    Select the route and complete any form

    Choose the requested tag or route, then answer the form questions. Include the specific detail the support team needs, but do not submit passwords, private keys, recovery codes, or other secrets.

  3. 03
    Continue in the private ticket channel

    After successful creation, use the new ticket channel for follow-up context and attachments. If you cannot see the channel, do not retry repeatedly; ask a server administrator to check the bot's permissions and the ticket record.

How staff manage the request

StateMeaningTypical next action
OpenNeeds triage or active work.Review, claim, or set priority.
ClaimedA staff member owns the request.Investigate and record useful notes.
PendingWaiting on information or a prerequisite.Explain what is needed, then resume.
ReopenedA closed request needs follow-up.Review the prior history and continue.
ClosedThe active conversation is finished.Confirm transcript/archive steps completed.
ArchivedNot part of the active queue.Consult the retained record if needed.

04STATE & FAILURE SAFETY5 MIN READ

Ticket safety, duplicate prevention & close order

A reliable support flow needs to handle double-clicks, retries, stale UI, and permissions without treating each click as permission to create another support request. These safeguards reduce duplicate work, but they do not remove the need to check the live ticket state when an interaction looks uncertain.

When a ticket request seems stuck

  1. 01
    Check the existing ticket before retrying

    Look for the active ticket channel and its current status. The bot documents duplicate-open prevention based on persisted status plus ticket-creation cooldown handling. Repeating the same click quickly can create confusing feedback or hit a cooldown even when the first request partly succeeded.

  2. 02
    Read the state, not only the channel name

    Names are labels for humans. ResolvX keeps an explicit state in ticket metadata and persists ticket records in PostgreSQL-backed storage. If a ticket appears in the wrong category or has an unexpected name, inspect its controls and history before moving resources manually.

  3. 03
    Use the matching lifecycle action

    Use Claim when staff accepts ownership, Unclaim to return responsibility to the shared team, Pending while a prerequisite is missing, Resume when work can continue, Reopen for follow-up after closure, and Archive when the record should leave the active queue.

What the states mean operationally

StateInterpretationOperator check
OpenAvailable for triage or current work.Check owner, department, tag, and priority.
ClaimedA staff member has taken responsibility.Check that the owner is still correct.
PendingWaiting on a response or prerequisite.Tell the member what is missing.
ReopenedA previously closed request needs follow-up.Read the old history before continuing.
ClosedThe active exchange is finished.Check transcript and channel-lock results.
ArchivedThe ticket is retained outside the active queue.Consult recovery/retention guidance before deletion.

Why the close order matters

The documented safe close sequence captures the transcript, confirms the upload succeeded, locks channel access, records the closed state, refreshes relevant controls, and only then applies final naming or placement changes. This order avoids making the conversation unavailable before its record is saved. Test the transcript destination and permissions in a non-production guild before treating it as a compliance archive.

!
A timeout does not prove that nothing happened.

If Discord returns an expired-interaction or timeout message, inspect the ticket and audit record before repeating a destructive action. If the record is missing or inconsistent, use the repair/recovery path rather than editing database JSON or recreating resources by guesswork.

05ROUTING4 MIN READ

Departments and tags

Departments describe who should handle a request. Tags describe what kind of request it is. Good routing is specific enough to help without forcing members to study your internal org chart.

Configuration steps

  1. 01
    List the current departments

    Use Settings → Departments or /supportforge category list. Review current channel/category mappings before making changes.

  2. 02
    Create or edit a department

    Use the category-add or department-edit route to create a clear destination. Decide which staff roles own the queue and confirm permissions in Discord.

  3. 03
    Add focused tags

    Open Manage Tags and create labels for the main request types inside that department. Rename or remove tags only after checking active-ticket constraints and any panel/form mappings that depend on them.

  4. 04
    Test routing from a member account

    Submit one ticket for each important route and verify its category, access, and form questions. A pretty button that routes to the wrong team is still the wrong button, merely dressed better.

Design tip: one department can have several tags; for example, Account Help can include Login, Verification, and Account Recovery. Keep tag names short, understandable, and mutually distinguishable.

06INTAKE DESIGN6 MIN READ

Ticket forms and reusable templates

Forms collect context before the staff member has to ask for it. The documented form engine supports versioned schemas, answer validation, conditional fields across steps, lifecycle controls, and reusable templates.

Build a form from the Settings dashboard

  1. 01
    Open Settings → Ticket Forms

    Start a new draft and give it a name that explains the request it is meant to collect.

  2. 02
    Add the required questions

    Ask only what the team needs to triage or investigate the request. Make labels concrete. Prefer “Which order number is affected?” over “Give us details.”

  3. 03
    Set validation and conditional flow

    Choose the supported field schema and validation options shown by the form builder. Use conditional follow-up questions only when an earlier answer makes them relevant. Review the form schema and field guide if a rule is unclear.

  4. 04
    Save a template when the structure is reusable

    Templates allow a useful structure to be reused across forms without treating the template as the active form itself. Inspect the template before applying it.

  5. 05
    Activate, route, and test

    Activate only after checking all required fields, branching, and destination tags. Then test the form through a member-facing panel, not only in the admin preview.

Form commands

!
Check pinned form versions.

A form-target panel button can refer to a specific active form version. If the form changes, retarget and republish the panel when needed; otherwise the published entry point may no longer match the form the administrator intended.

07PUBLIC ENTRY POINTS6 MIN READ

Build and publish custom ticket panels

A panel is a public message with buttons that direct members into a configured support flow. The visual builder is intended to make that configuration manageable without editing JSON or source code for routine changes.

Recommended panel workflow

  1. 01
    Create a draft

    Go to Settings → Ticket Panels and create a new panel. Drafts are safe places to make edits without changing the currently published message.

  2. 02
    Add and configure buttons

    Choose a department or an active form target. Edit each button's label, emoji, style, optional tag, allowed roles, and optional confirmation message. Reorder buttons with the Move Up and Move Down controls.

  3. 03
    Set the panel appearance

    Configure the title, instructions, footer, accent colour, author icon URL, thumbnail, and banner image URL where the builder offers them.

  4. 04
    Preview privately

    Use the private preview to inspect wording and order. Preview controls are disabled by design so a preview cannot accidentally open tickets.

  5. 05
    Publish to a text channel

    Choose an accessible target channel and publish. Check the posted message from a non-administrator account before announcing it to members.

  6. 06
    Edit by republishing

    Change the draft and publish a new snapshot when the live panel should change. A draft edit alone does not update the already-posted panel. Delete a panel only after reviewing the confirmation; tickets already created from it are intended to remain.

08STAFF WORKFLOW5 MIN READ

Priority, ownership, participants, notes & history

These tools are meant to keep collaboration close to the ticket, rather than scattered across staff DMs and vague recollections.

Set a meaningful priority

The documented order is Critical → Urgent → High → Normal → Low. Agree what each level means for your organization. Use Critical or Urgent for genuine exceptions rather than as a decorative way of asking for attention.

Claim or hand off a ticket

Claim when someone takes responsibility. Unclaim when the request needs to return to a shared queue. Use Reassign for a deliberate change of owner or team. Check the visible owner before beginning duplicate work.

Add staff notes

Notes should capture diagnostic steps, decisions, and follow-up context useful to another authorized staff member. They should not contain passwords, private keys, payment credentials, or unrelated personal details.

Manage participants

Add a person only when they need access to the support conversation. Remove access when it is no longer required. Reassignment and participant controls should be preferred over manual permission edits so the ticket state and channel access can stay aligned.

Read the history

Use Ticket History before asking a member to repeat information or before retrying an action. It is intended to expose recent audit events associated with the ticket.

09REPORTS & VOICE4 MIN READ

Report intake, categories and voice actions

Report intake

Reports are a separate operational path for raising and classifying concerns. Configure report categories and subcategories that match the team's policy, then set the rules and thresholds for intake. When submitting a report, check the category, subcategory, participant, and target carefully before choosing whether to flag or record it without a flag when that option is shown.

  1. 01
    Configure the taxonomy

    Open Settings → Reports to manage categories, subcategories, and report rules.

  2. 02
    Use the ticket report control

    Choose the correct subject and reason, review the details, then submit the intended action.

  3. 03
    Review the outcome

    Use available ticket/audit history and the server's moderation process to follow up. Do not treat a recorded report as a verified finding by itself.

Voice-related ticket actions

Voice tools can support a live conversation when text is not enough, but they depend on the host server's permissions, channel configuration, capacity limits, and bot version. Review Settings → Team & Voice, test start/join/end in a dedicated server, and record the outcome in the ticket where appropriate.

10ARCHIVE & RECOVERY7 MIN READ

Ticket archive and recovery guide

Recovery tries to preserve a useful record when a ticket channel is deleted. It cannot undo Discord's deletion itself; it creates a replacement channel and reconstructs supported content from records that were already saved.

What the archive may preserve

  • Observed ticket messages, text, original timestamps, author ID/name snapshots, embeds and component payloads.
  • Attachment metadata, and attachment bytes when they were successfully downloaded from Discord and fit the configured size limit.
  • Edits, observed deletions, and channel configuration such as the name, topic, parent, position, rate limits, NSFW flag, and permission-overwrite bitfields.
  • Deletion source, confirmation stage, review answer, and replacement-channel linkage for supported flows.

Native deletion versus intentional ticket deletion

DISCORD-NATIVE CHANNEL DELETE

Intent unknown

If someone deletes the channel through Discord itself, the record is identified as a native deletion. The documented review path is Settings → Repair System → Restore Channel. This path does not automatically imply that the owner intentionally closed the ticket.

DELETE TICKET CONTROL

Two confirmations

Deleting from the ticket's own control is designed to require two separate confirmations and to record the button intent before calling Discord. The record enters Ticket Deletion Review, which asks whether the ticket was deleted by mistake.

Restore checklist

  1. 01
    Open the right recovery queue

    For a native delete, open Settings → Repair System → Restore Channel. For a deletion initiated through the ticket control, review Ticket Deletion Review.

  2. 02
    Answer the mistake question accurately

    The ticket-control flow is designed to record the review answer and reviewer in Neon and in the ticket/developer audit streams. A bot-initiated ticket deletion is restored only after the reviewer selects Yes.

  3. 03
    Start the supported restore action

    The recovery process creates a replacement private channel, rebuilds the supported ticket controls, and replays available archived messages in chronological order.

  4. 04
    Inspect the new channel

    Check the channel permissions, topic, content, attachments, and replacement channel linkage before staff resume support.

!
Recovery has real limits.

The original channel/message IDs, original Discord authorship, reactions, arbitrary live components, and expired external media cannot be restored as if deletion never happened. Replayed text is sent by the bot and marked with original metadata; the bot does not impersonate users. Messages deleted before they are archived may be missing. An attachment whose bytes were not stored can only be represented by its available metadata.

Keep regular database backups and respect your community's retention policy. Archive storage, especially attachment bytes, consumes database capacity. Do not promise that every historical message or file can be recovered.

12WORKSPACE USABILITY4 MIN READ

Panel activity & ticket-control placement

Ticket-control placement manages where the bot's controls sit relative to a ticket conversation. It is separate from the public support panel members click to open tickets, and separate again from inactivity auto-close.

What the thresholds control

VISUAL BUDGET

Keep controls visible

The visual-line budget is a layout threshold used to decide when the control message should move. It is not a message count, SLA timer, or support-hours setting.

MESSAGE BUDGET

Avoid control sprawl

The message safety cap and minimum-message threshold help avoid movement on every single reply. Use conservative values first and watch a real ticket before tuning them further.

The command definition validates a visual budget between 6 and 40 lines, a message safety cap between 5 and 30 messages, and a minimum-message threshold between 3 and 20. The server can inspect the setting, toggle it, enable or disable it, and adjust those thresholds.

Recommended tuning workflow

  1. 01
    Start by inspecting current settings

    Use the Settings dashboard or slash command before changing any values.

  2. 02
    Change one threshold at a time

    Use a test ticket with realistic conversation volume. If controls move too frequently, tune the message cap or minimum count; if they are pushed out of view, review the visual budget.

  3. 03
    Keep it distinct from inactivity closure

    Control movement does not mean a ticket is idle. Inactivity automation has its own warning interval, grace period, and exemptions.

i
“Panel” can mean two things

The public support entry panel is member-facing. The ticket-control panel belongs to an existing ticket. Command context makes clear which one is being adjusted.

13DATA STEWARDSHIP3 MIN READ

Retention review and approvals

Retention controls are intended to help the administrator review which supported records may qualify for cleanup. The presence of a retention policy should not be interpreted as permission to delete anything without review.

  1. 01
    Define the policy

    Choose an appropriate record lifecycle for your organization and understand which data types the configured policy applies to.

  2. 02
    Review candidates

    Open the retention review and inspect which records are eligible. Consider active disputes, operational requirements, and legal or contractual retention obligations.

  3. 03
    Approve deliberately

    The documented action flow requires explicit approval before supported removal operations. Confirm the target and consequences before approving.

  4. 04
    Maintain a separate policy

    Document the server's retention and privacy policy. Account for database backups and attachment storage separately; do not promise a deletion timeline you have not verified.

14ACCOUNTABILITY4 MIN READ

Audit tools and diagnostics

Audit summaries make support activity easier to review. Restricted developer views help authorized maintainers inspect system-level or recovery-related events. These tools should remain limited to people who need them for a defined operational purpose.

Review audit information

  1. 01
    Choose an appropriate summary

    Use a quick or overall summary for orientation and a daily summary when the review is tied to a date or operational shift.

  2. 02
    Review accumulation carefully

    Understand what the enable, revert, or clear/confirm action will do before changing audit retention settings.

  3. 03
    Use Developer View only when authorized

    The developer view is access controlled. Restrict the destination channel and users, and avoid sharing internal diagnostics publicly.

  4. 04
    Keep a human-readable resolution

    Document the outcome through your team's accepted procedure so future administrators know what was changed and why.

!
Raw audit data is sensitive operational information.

15RELIABILITY & HOSTING5 MIN READ

Storage, retries, updates and deployments

Durable storage

Neon PostgreSQL is the intended production source of truth for ticket metadata, configuration, archive records, deletion intent, and recovery progress. The bot documentation explicitly says not to use SQLite as the live persistence provider. Legacy SQLite migration/repository files are retained for compatibility and test use only.

Why retries and the outbox matter

Discord can respond with a rate limit, an interaction can expire, or a network request can fail after some work has completed. A durable outbox helps represent work that needs retrying instead of silently forgetting a required follow-up. It does not make Discord and PostgreSQL a single atomic transaction, so recovery flows must still track progress and acknowledge edge cases.

Automatic update option

The project documents GitHub Actions CI and an optional server-side Linux/systemd self-update watchdog. The watchdog is an operator-configured deployment feature; it does not automatically install itself on every host. Secure the deploy credentials, review what branch/ref the updater trusts, test restarts, and retain a rollback procedure.

Useful maintenance references

For code changes, use CI build and test results alongside a live test-guild check. Do not run destructive database tests against the production Neon URL. Store environment values in the runtime environment, not in this website.

16LANGUAGE & OPERATIONS6 MIN READ

Languages, support hours & automation

ResolvX now has a server-level message-language setting, time-zone-aware support-hours configuration, an inactivity policy, and a choice of workspace type for new tickets. These controls solve different problems: locale changes supported bot copy, hours define when intake is allowed, inactivity governs stale conversations, and workspace settings decide where a ticket lives.

BOT MESSAGES

Twenty-one supported locales

The Stage H localization catalog covers English (United States), Hindi, Bengali, Spanish, French, German, Brazilian Portuguese, Arabic, Japanese, Italian, Indonesian, Korean, Russian, Simplified Chinese, Turkish, Dutch, Polish, Ukrainian, Greek, Czech, and Swedish. Choosing a locale sets the language used by supported ResolvX messages in that server.

Localization is intentionally bounded. It does not automatically translate what a member types, user-created ticket titles, descriptions, form answers, server names, tags, persistent IDs, audit action codes, or every legacy message that has not yet been migrated.

PUBLIC WEBSITE

Translate the documentation

The language control in the site navigation can request a machine translation of public page text. This is separate from the bot locale. Website translation uses a third-party translation endpoint, may be inaccurate or unavailable, and sends public documentation text to that provider. The site does not send Discord tickets or server data to the translator.

Code samples and command names are excluded from ordinary text-node translation. Choose English to restore the original text if a translation looks wrong.

Set the bot's message language

An administrator can use the private Settings dashboard's Server Language control or the command below. The setting is stored in the existing server-settings document, with English as the safe default. The catalog and its command are available in the Stage H branch; deploy only after CI and live-guild acceptance checks succeed.

Configure support hours and time zone

Support hours can be configured at the server default level or overridden for a department or a ticket panel. Use an IANA time-zone identifier such as Asia/Kolkata, then configure each weekday with one or more intervals. For example, 09:00-12:00,13:00-17:00 defines a split day; use closed for a day without a scheduled opening.

The outside-hours behaviour controls whether new tickets are allowed or restricted when the schedule is closed. A panel or department override should be checked separately from the server default so administrators know which schedule is effective. This feature is intake scheduling, not a complete SLA engine, on-call rotation, or promise that an agent is available during every open period.

Choose a ticket workspace

New tickets can use private text channels or private threads. Channels and threads have different permission models, moderation behaviour, membership rules, and capacity limits. Check the bot's permissions and your server's intended staffing workflow before switching the mode. This setting applies to new tickets; do not assume it migrates existing tickets.

Understand inactivity automation

The inactivity policy can be inspected or enabled/disabled, and configured with an idle period before a warning and a grace period before automatic closure. Administrators can manage exemptions for roles and departments so conversations that should not be auto-closed are excluded. Choose conservative periods, explain the warning to members, and test exemptions before enabling automation in a live support server.

Inactivity closure is not the same as an SLA timer. It does not establish a response-time guarantee or measure whether staff met a contract. Test how reopen and archived-ticket flows behave before enabling it for all tickets.

Panel-activity settings are separate

The panel activity controls define a visual line budget, a message safety cap, and a minimum number of messages before moving ticket controls. They tune the ticket-control placement workflow. They are not the same as support opening hours or ticket inactivity auto-close, and they should be adjusted independently.

Deployment status matters.

The bot locale catalog and controls are being delivered through Stage H Part 2. Build and automated tests must pass, commands must be registered from the updated branch, and each chosen language or automation policy must be checked in a non-production Discord guild before production reliance.

17SCHEDULING5 MIN READ

Support hours & time-zone rules

Support hours describe when ticket intake is allowed under a server's configured schedule. They are not an SLA timer, an agent shift roster, or a promise about response time. A schedule is only useful when its time zone and outside-hours policy match the team's actual operating hours.

Configure a schedule safely

  1. 01
    Choose an IANA time zone

    Use a full identifier such as Asia/Kolkata, Europe/Amsterdam, or America/New_York. Do not enter a fixed UTC offset when you mean a region that observes daylight-saving changes.

  2. 02
    Define each weekday

    The supported schedule format accepts intervals such as 09:00-12:00,13:00-17:00 for a split shift, or closed for a day without an opening window. Check the command picker for the exact field requirements of your deployed bot.

  3. 03
    Choose the scope

    The server default is the baseline. A department or ticket-panel override can be configured when that support path genuinely follows a different schedule. Include the matching scope ID only for an override.

  4. 04
    Set outside-hours behaviour

    The current controls distinguish allowing new tickets outside opening hours from restricting ticket creation. Decide whether people may leave a request at any time or must wait until the next configured opening.

  5. 05
    Test boundary times

    Test just before opening, exactly at opening, during a split-shift break, after closing, and across a daylight-saving boundary if relevant. Confirm both the displayed time and the intake decision.

!
Support hours are not a full SLA engine.

They govern configured intake windows and outside-hours behaviour. SLA policies, escalation clocks, queue targets, and business-hour reporting remain outside the current feature promise unless a future release explicitly implements them.

18OPT-IN AUTOMATION5 MIN READ

Inactivity warnings & automatic closure

Inactivity automation is designed for stale conversations, not for managing staff shifts. When enabled, it can warn about a quiet ticket and allow a grace period for a reply before attempting automatic closure.

Policy components

Idle intervalHow long the ticket is inactive before the warning stage.
Grace periodHow long the owner has after the warning to resume the conversation.
ExemptionsRole and department exceptions that keep eligible tickets out of auto-close handling.

The slash command accepts an idle threshold from 1 to 720 hours and a grace period from 1 to 168 hours. It can be enabled, disabled, inspected, or reconfigured. Role exemptions matter when the ticket owner or assigned staff holds an exempt role; department exemptions apply to that department's tickets.

Recommended rollout

  1. 01
    Start disabled while policy is reviewed

    Choose thresholds that account for weekends, holidays, and the team's normal response time. Auto-close should not surprise members who have been told to expect a slow reply.

  2. 02
    Configure exemptions first

    Identify VIP, moderation, escalation, or long-running technical departments that should not be closed by the same idle policy. Verify role and department IDs before enabling.

  3. 03
    Test warning and grace stages

    Confirm a warning appears at the expected time, a member reply cancels pending closure as intended, and closed tickets still follow the configured transcript and retention path.

  4. 04
    Audit policy changes

    Changing the enabled state, thresholds, or exemptions advances the policy generation and clears applicable existing inactivity warnings. Recheck test tickets after a policy change.

!
Keep destructive automation opt-in.

Agree the warning text, grace interval, role exemptions, staff expectations, and archive/retention policy first, then verify the configuration in a test guild.

19CHANNELS & THREADS4 MIN READ

Private text channels vs private threads

The workspace setting chooses which Discord resource type is used for new tickets. It changes the shape of new workspaces, not the identity or historical contents of tickets that already exist.

PRIVATE TEXT CHANNEL

Dedicated channel

A separate text channel has its own channel permissions and category placement. This is often simpler to reason about, but creates more channels and depends on correct permission overwrites and category permissions.

PRIVATE THREAD

Thread workspace

A private thread keeps the conversation under a parent text channel and relies on thread membership and server permissions, including the bot's ability to create/manage threads. Parent-channel permissions and staff access need deliberate testing.

Switching the workspace mode

  1. 01
    Check server and bot permissions

    For channels, check manage-channel and permission-overwrite behaviour. For private threads, verify thread creation, visibility, membership, archive/unarchive, and staff access.

  2. 02
    Set the mode for new tickets

    Use the Settings dashboard's Ticket Workspace control or the slash command to inspect or select private text channels/private threads.

  3. 03
    Create a real test ticket

    Test with a member, regular staff, an administrator, and a user who should not have access. Verify that no one can read a ticket they should not see.

  4. 04
    Keep old tickets in mind

    Changing the default does not convert existing tickets from a channel into a thread or vice versa. Handle any migration separately.

20TEST ENTITLEMENTS3 MIN READ

Premium demo controls

The current premium controls are demo entitlement tools. They help test how entitlement state is represented, but they are not a connected payment system and should not be described as a purchase flow.

What an administrator can do

The bot provides a status command and a demo toggle for its supported tiers. Treat the resulting tier as test/configuration state only. There is no claim here that a payment has been collected, a subscription exists, a card is stored, or an entitlement has been verified with a billing provider.

!
Demo state is not billing.

Do not use this setting to represent paid customer entitlements or collect payments. Real subscriptions, billing webhooks, invoices, cancellation, and payment reconciliation are outside the current feature set.

21ACCESS & SAFETY5 MIN READ

Permissions, authorization & destructive actions

ResolvX uses several different kinds of access checks: who may configure a server, who may use a staff action, which roles may enter a custom panel, and which members can see a ticket resource. These checks are related but not interchangeable.

Access boundaries to test

  • Server administration actions require Manage Server or Administrator where the command is gated for administrators.
  • The Settings dashboard checks that controls are used from the recognized ResolvX Settings channel; the Staff Manual has a documented exception for configured department staff.
  • Ticket actions validate the user and ticket context rather than assuming that knowing a command path is authorization.
  • Custom panel and button role restrictions are combined and checked again at click time; confirmation is bound to the initiating user and source published message.
  • Private-channel and private-thread workspace choices need their own live permission review.
  • Destructive controls such as factory reset and retention deletion use explicit confirmation or approval steps.

Before a production rollout

Create an acceptance matrix with a normal member, department staff, an administrator, and a user who is deliberately not authorized. Test the same operation through every documented entry point available in the deployment. Verify both allowed and denied results, and review the audit record for sensitive settings changes.

!
Never test destructive actions against production records.

Use a dedicated guild and non-production database. Never paste Discord tokens, database URLs, or other secrets into public issues, screenshots, or diagnostic output.

22DIAGNOSIS & RECOVERY6 MIN READ

Troubleshooting common bot errors

A stack trace is useful when you isolate the first error and identify whether it happened during startup, command registration, a Discord interaction, persistence, or an external request. The entire console dump is rarely the best starting point.

SymptomLikely layerSafe next check
Slash command build/deploy fails around settingsCommand declaration limitsUpdate to the current command definition and re-run command deployment. Report taxonomy commands use the sibling settings-reports group so Settings stays within Discord's 25-subcommand cap.
Unknown Interaction / interaction expiredDiscord acknowledgement timingCheck whether the interaction was deferred/replied in time. Inspect ticket state before repeating the action.
Unknown Message / stale panel controlDeleted or replaced Discord messageRefresh the appropriate Settings/public panel and confirm which published message is current. Do not treat a stale pointer as permission to delete unrelated messages.
Database connection timeout or unavailableNeon/PostgreSQL connectivityCheck the configured DATABASE_URL/provider, runtime networking, connection limits, and CI logs. Do not replace production Neon with SQLite as a workaround.
Rate limit / retry-after responseDiscord API throttlingRespect the indicated delay and let the retry/outbox path finish where supported. Repeated clicking can stack unnecessary requests.
Missing channel or recovery recordDiscord-side deletion or incomplete setupUse the Settings repair/recovery path, inspect audit history, and verify what archive data exists before manually rebuilding anything.

Collect a useful diagnostic packet

  1. 01
    Capture the first error and its stack

    Include the action, whether it happened on startup or after an interaction, the first error message, top relevant source lines, and timestamp. Remove tokens and connection strings.

  2. 02
    Confirm code version and command registration

    Check the branch/commit and CI result. After a slash-command definition changes, deploy registered commands using the repository's script and verify the expected paths in Discord.

  3. 03
    Inspect state before rerunning

    Check the ticket record, channel topic, audit log, and transcript destination before retrying a failed close, restore, or deletion.

  4. 04
    Use the smallest safe reproduction

    Use a test guild and non-production database. Reproduce one action at a time with the same permissions and resource type, then compare logs and audit output.

i
Share the shortest useful excerpt.

Do not paste a full environment dump or credentials. A focused error message, sanitized stack trace, branch/commit, and the precise failed action are usually enough to start.

25FREQUENTLY ASKED QUESTIONSREFERENCE

Frequently asked questions

The questions people ask before installing a support bot, during setup, and when something inevitably behaves in a way that makes everyone question software as a concept.

What does ResolvX do?

ResolvX is a Discord-first support ticket system. It is intended to structure incoming requests, route them to the right team, track ownership and state, preserve useful history, and give administrators controls for forms, panels, settings, reporting, audit, and recovery.

Can I invite the bot from this website?

No invite is exposed here. This website is a static documentation site and is not connected to Discord. Use the bot repository and the project's actual deployment or invitation instructions when a verified installation link is available.

Does the website run bot commands or show live tickets?

No. The forms, visual mockups, command copy buttons, and lifecycle simulator are front-end documentation aids. They do not log in to Discord, create tickets, change settings, or read server data.

Why do command examples say /supportforge instead of /resolvex?

The current bot source documents the /supportforge root. ResolvX is the product identity used by the site. Slash-command names are registered separately in Discord and may change in a future release; always use the names your deployed bot actually exposes.

What does a member do to open a ticket?

Use a published support panel, choose the appropriate department or form target, select the relevant route/tag if prompted, complete required form questions, and continue in the ticket channel that is created. Availability and wording depend on the server's configuration.

Can I customize multiple public support panels?

The repository documents a visual multi-panel builder. Each panel may include department or active-form targets, customized labels and emoji, ordering, role access, confirmation text, and selected branding fields. Draft edits need to be published before they change the live message.

Are form templates the same as active forms?

No. A template stores a reusable structure. Applying a template creates or updates a form workflow, while activation and panel routing are separate steps. Test the resulting form from the member-facing path.

Can ResolvX restore a deleted ticket exactly as it was?

No. Recovery creates a replacement channel and replays available archived records with original metadata labels. Discord does not let the bot restore the original IDs or impersonate original authors, and reactions, arbitrary live components, expired media, and messages not archived before deletion cannot be guaranteed.

What happens to attachments during recovery?

Attachment metadata may be retained. The bytes are restorable only if the archive successfully captured them from Discord and they fit the configured size limit. Large or inaccessible files may be listed without having their original bytes available.

Which database should production use?

The bot README specifies Neon PostgreSQL as the production durable store and explicitly disallows SQLite as the live persistence provider. Configure the current environment variables and migrations documented by the bot repository.

Are slash commands and button controls both supported?

The implementation requirements document independent command and button entry points for major features. However, actual permission combinations, select menus, and live server behavior still need acceptance testing on the deployed version.

Does Premium demo mode mean billing is connected?

No. A demo-toggle and status control is not real payment processing or a production billing system. Treat it as a test surface for entitlement-dependent behavior only.

What should I check if a button or command does nothing?

Check whether the command is registered, whether the bot is running, whether the interaction timed out, whether the actor has the required permissions, whether the target channel/role still exists, and whether the database connection is healthy. Reproduce in a test guild and inspect the logs before retrying destructive actions.

Can I hide repair or destructive controls when customizing Settings?

The Settings Layout builder is documented to retain repair, refresh, and Delete Everything controls. Their availability and safety styling are intentionally protected, rather than being ordinary navigation items that can be hidden through visual customization.

Does ResolvX provide AI answers, a knowledge base, SLA timers, or customer satisfaction surveys now?

AI answers, a built-in knowledge base, a workflow graph editor, an SLA engine and CSAT surveys remain roadmap areas. Stage H adds twenty-one bot-message catalogs for supported strings and a separate website translation control, but this is not complete translation of every legacy bot message or user-authored ticket content.
