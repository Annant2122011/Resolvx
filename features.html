01TICKETS
REQUEST MANAGEMENT

Ticket lifecycle & controls

Live acceptance required

A ticket is a tracked support request, not merely a private channel. ResolvX documents explicit lifecycle states so staff can distinguish a new request, work with an owner, a waiting item, a reopened issue, a closed conversation, and an archived record.

Open

New or active request that needs review or action.

Claimed

A staff member has taken ownership of the request.

Pending

Work is waiting for information or another prerequisite.

Reopened

A previously closed conversation needs attention again.

Closed

The active support interaction has been closed.

Archived

The request has moved out of the active working queue.

How staff use it

  1. Open the ticket from its private channel or the server's configured panel.
  2. Review the message and intake answers before changing its state.
  3. Claim or reassign ownership, then set the priority and add staff-only notes as needed.
  4. Use Pending when waiting; resume when actionable work can continue.
  5. Close only after the issue is addressed and the required close workflow has completed. Reopen when follow-up is needed.
  6. Archive when the record should leave the active work area but remain part of the supported history.

Command entry points

The current code documents the command root as /supportforge. Branding and command registration can evolve independently; use the commands shown by your deployed bot.

02ROUTING
STRUCTURED INTAKE

Departments, categories & tags

Live acceptance required

Departments group requests by the team or subject responsible for helping. Tags add a more specific label, such as the request reason, product area, or issue class. Together, they reduce the amount of guesswork required to send a request to the right place.

Recommended setup

  1. Decide which teams genuinely own different kinds of support. Avoid creating a separate department for every tiny topic.
  2. Create or review departments through Settings → Departments or /supportforge category add.
  3. Open Manage Tags for the department and add a short, distinct tag for each request type.
  4. Give each tag a clear meaning and remove duplicates that staff cannot distinguish.
  5. Test the member-facing selection flow and confirm that the resulting ticket appears in the expected category.

Useful command paths

A tag must remain meaningful to the workflow. Check active-ticket and permission constraints before changing existing routing.

03INTAKE
BETTER QUESTIONS, EARLIER

Versioned forms & reusable templates

In repository

Forms collect relevant facts before or during ticket creation. ResolvX's documented form system includes versioned schemas, answer validation, conditional fields across steps, activation controls, routing metadata, and a template workflow. The aim is to prevent support agents from having to ask the same preliminary questions repeatedly.

How an administrator builds a form

  1. Open Settings → Ticket Forms and create a draft form with a clear name and purpose.
  2. Add the questions required to diagnose the issue. Use labels that members understand and validation that catches incomplete or incorrectly shaped answers.
  3. Use conditional fields only when a follow-up question genuinely depends on an earlier answer. Keep the flow short enough that members will finish it.
  4. Review the schema and supported field rules, then update and validate the form.
  5. Save a reusable template when the structure will be useful for another form; list or apply templates from the form tools.
  6. Activate the form only after its question flow and routing have been checked. Retest it from the actual member-facing entry point.

Form command family

Templates and live forms are separate objects. Applying a template is not the same as publishing or activating a form.

Versioning matters.

Published panel buttons can target a specific active form version. If that version changes, an administrator may need to retarget the form button and republish the panel so the public entry point points at the intended form.

04CUSTOMIZATION
DESIGN THE ENTRY POINT

Visual ticket-panel builder

In repository

A panel is a published message that gives members one or more ways to start the right support flow. Multiple panels let an administrator separate, for example, billing help from technical support without forcing everyone through one generic menu.

✳

Target-aware buttons

A button can target a department flow or a specific active form with concrete routing metadata.

◎

Control over access

Configure allowed roles, optional confirmation text, and labels or emoji that make each option easy to identify.

▧

Branding and order

Customize title, instructions, footer, accent colour, icon, thumbnail, banner, and button order.

↻

Draft, preview, publish

Review a private disabled preview before publishing the version intended for members.

Recommended publishing workflow

  1. Go to Settings → Ticket Panels and create a draft.
  2. Add one button per distinct route. Choose a department or active form target.
  3. Set each button's label, emoji, style, access roles, optional tag, and confirmation text.
  4. Reorder the controls; then check the private preview at desktop and mobile widths.
  5. Choose an accessible text channel and publish.
  6. When editing a live panel, change the draft and republish. Do not assume draft edits changed the message already posted to Discord.

Panel command family

Discord component limits cap a panel at 25 buttons. Private preview reserves a row for navigation, so very large drafts may show fewer controls in preview than in a published panel.

05COLLABORATION
A SHARED VIEW OF THE WORK

Ownership, priority, participants & notes

Live acceptance required

Support work gets messy when no one knows who owns a request, which issue is urgent, or what the last staff member tried. Ticket controls are intended to keep those decisions close to the conversation and apply role and state validation before a change is saved.

Priority

Set urgency according to the team's policy. The documented order is Critical, Urgent, High, Normal, then Low. Avoid marking every request as urgent; a signal that applies to everything conveys very little.

Claim and reassign

Claim a ticket when taking responsibility. Reassign deliberately when another person or department is better placed to finish the work. Unclaim if ownership needs to return to the shared queue.

Staff-only notes

Record internal context that helps the next staff member. Notes should be factual and relevant; don't place secrets or unnecessary personal data in them.

Participants

Add or remove people when someone needs access to the ticket conversation. Re-check access after a hand-off, and use the available controls rather than manually guessing permission overwrites.

06OVERSIGHT
CONTEXT AND ACCOUNTABILITY

Ticket history, reports & intake rules

Live acceptance required

Ticket history helps staff understand what changed and when. Report intake provides a structured way to raise concerns using categories and subcategories, with rules for whether an item is recorded or flagged for action. These are separate workflows: a report is not the same thing as a customer-support ticket.

Review a ticket or submit a report

  1. Use Ticket → History to view recent events for the request before repeating work.
  2. For a report, open the ticket Report control or the matching slash command.
  3. Choose the applicable report category and subcategory, and review the target or participant details carefully.
  4. Select the intended action, such as flagging the item or recording it without a flag, where the workflow offers that choice.
  5. Administrators configure report categories, rules, and thresholds under Settings → Reports.

07COMMUNICATION
WHEN TEXT ISN'T ENOUGH

Ticket voice actions

Server configuration required

Voice-related ticket actions are documented for teams that need a live conversation in addition to written support. Voice workflows depend on the server's channel setup, staff permissions, platform support, and the deployed bot's configured limits.

How to use voice responsibly

  1. Review the server's voice capacity and relevant permissions in Settings → Team & Voice.
  2. Use the ticket voice controls or the voice command family to start, join, or end the appropriate session.
  3. Invite only people who are participants in the support request and are allowed to access it.
  4. End the session when the conversation is complete and record any necessary outcome in the ticket.

Command entry point

Test channel creation, visibility, joining, and cleanup in a dedicated test server before making voice support part of a production procedure.

08RESILIENCE
RECOVERY WITH HONEST LIMITS

Ticket archives & channel recovery

Limits apply

The archive is intended to preserve observed ticket messages and channel metadata in durable storage. Recovery can create a replacement channel for supported deletion cases and replay the messages that were successfully archived. It is a safety net, not a time machine with administrator powers over Discord's history.

1Observe & archive

Store supported message content, author snapshots, timestamps, embeds, attachment metadata, and channel configuration in Neon.

→
2Review deletion intent

Distinguish native channel deletion from a ticket deletion initiated through the bot's confirmed flow.

→
3Restore a replacement

Create a new private channel, restore supported controls, and replay saved messages with original metadata clearly labelled.

What administrators should do

  1. Keep the bot running with the required channel and message access so its background archive can observe history.
  2. For a native channel deletion, check Settings → Repair System → Restore Channel.
  3. For a deletion requested from the ticket's own Delete Ticket control, review Ticket Deletion Review and answer the mistake question accurately.
  4. Inspect the replacement channel, permissions, and replayed content before returning it to normal use.
  5. Keep routine Neon backups. Recovery should not be the only copy of important records.

Important boundaries

  • Original Discord channel, message, and author IDs are not recreated.
  • Replayed messages are sent by the bot and labelled with saved author/channel/message metadata; the bot does not impersonate users.
  • Only attachment bytes successfully archived within configured limits can be reattached.
  • Reactions, arbitrary live component state, and expired external media cannot be guaranteed.
  • Messages that were deleted before they were archived may be unavailable.

09ADMINISTRATION
PER-SERVER CONFIGURATION

Settings dashboard, appearance & layout

In repository

The Settings dashboard is the operator's home for server-level configuration. Documented controls include themes, default ticket behavior, team and voice capacity, retention, report settings, panel behavior, appearance, and maintenance. A separate layout builder customizes the Settings-channel navigation without changing public ticket panels.

Customize the Settings channel

  1. Open the persistent Settings dashboard and select Settings Layout.
  2. Edit the dashboard title, description, and footer to match the server's internal language.
  3. Reorder navigation buttons and customize their labels and emojis.
  4. Preview the layout privately. Remember that the preview controls are disabled and meant for review.
  5. Save the layout and return to the real dashboard. Check that administrators can still reach all required controls.

Two separate surfaces

Settings Layout changes the admin dashboard's navigation and wording.

Ticket Panels changes the public support entry messages members click.

They are stored separately. Editing one should not be expected to modify the other. Repair, refresh, and destructive reset controls remain protected and cannot be hidden by visual customization.

10DATA STEWARDSHIP
RETENTION WITH HUMAN REVIEW

Retention review & approved actions

Explicit approval

Retention controls are intended to help administrators review records that may be eligible for cleanup without treating deletion as an invisible background side effect. A proposed action should be reviewed against the server's retention policy and applicable obligations before it is approved.

Recommended operator flow

  1. Set the intended retention policy and understand what record types it affects.
  2. Open the retention review and inspect the eligible items before taking action.
  3. Confirm that the record is actually covered by the policy and is no longer needed for a legitimate support or audit purpose.
  4. Approve the supported action deliberately. Do not assume that merely opening a review deletes anything.
  5. Keep the team's retention policy and data handling procedure documented outside the bot as well.

Command entry points

Retention settings are not a substitute for a published data policy. Verify the deployed implementation, backups, attachment limits, and any separate storage lifecycle before promising a deletion timeline.

11OPERATIONS
SETUP AND MAINTENANCE

Setup, restore, repair & deployment

Operator configured

The repository documents setup and restore commands, storage and infrastructure repair controls, a GitHub Actions CI workflow, and an optional Linux/systemd self-update watchdog. These are maintenance tools for the deployed bot, separate from this static website.

Safe first setup

  1. Create and configure the Discord application and bot, and grant only the permissions it needs for the support workflows enabled in the server.
  2. Configure a Neon PostgreSQL database and the runtime variables listed in the bot repository's .env.example. Never paste tokens or connection strings into the website.
  3. Apply migrations, build, run tests, and register slash commands using the project's deployment documentation.
  4. Run setup in a non-production test guild first. Inspect the created categories, channels, permissions, settings panel, and public panel.
  5. Exercise ticket creation, state changes, closing, recovery, and admin permissions before onboarding real members.

Maintenance commands

Automatic GitHub updates are not magic. The optional server-side watchdog must be configured by the operator, and its host must have safe deployment credentials and an appropriate restart policy.

12ACCOUNTABILITY
SEE WHAT CHANGED

Audit summaries & developer view

Access controlled

Audit tools help authorized operators review a summary of support activity and investigate maintenance or recovery events. The developer view is a restricted diagnostic surface, not a public member feature. Controls that clear raw audit data or alter sensitive views should keep explicit confirmation and access checks.

How to review activity

  1. Open the Audit panel or run the matching audit summary command.
  2. Choose a quick, overall, or daily view depending on the question being investigated.
  3. Use accumulation controls only after understanding what data is retained or cleared by the selected action.
  4. Open Developer View only for users and channels authorized for that access.
  5. Record the investigation outcome through the server's approved operational procedure.

Command entry points

Destructive audit actions need extra care.

Clearing raw audit events is documented as confirmation-gated. Never bypass that confirmation or use developer tools to expose internal records to ordinary members.

13FOUNDATION
PERSISTENCE AND RESILIENCE

Durable storage & retrying operations

Architecture documented

ResolvX uses Neon PostgreSQL as its intended production source of truth for tickets and server configuration. A durable outbox pattern is documented for work that must be retried safely, because Discord API calls can fail, rate-limit, or be interrupted even when the underlying request remains valid.

PostgreSQL is not optional production trivia.

The bot README explicitly disallows SQLite as the live persistence provider. Legacy SQLite-related files exist for compatibility or tests only. Operators should use the current environment documentation and never run destructive integration tests against production data.

14ENTITLEMENTS
A SAFE DEMO SURFACE

Premium demo controls

Demo only

The repository documents a premium status and demo-toggle workflow. It is useful for testing UI and entitlement-dependent paths, but it must not be presented as real billing, a paid subscription, or proof that payments are connected.

How administrators should use demo mode

  1. Review the current premium status with the relevant settings control or command.
  2. Toggle demo status only in an environment where testing that state is intentional.
  3. Check the interface or path that depends on the state.
  4. Return demo mode to its intended state before treating the server as a production environment.

Command family

The website does not take payment, manage a subscription, or enable a premium entitlement in a real Discord server.

Clear answers.
No inflated promises.

All wiki FAQs →
Are all listed features available in production today?

No. Several feature areas are documented in code, but they still need live guild acceptance. Other capabilities are explicitly marked as roadmap work. The status labels are part of the feature descriptions on this page.

Why do some current command examples start with /supportforge?

The bot source currently documents that slash-command root. ResolvX is the product/site brand, but command registration is a separate implementation detail. Follow the command names registered by your deployed bot.

Can recovery restore every deleted message, reaction, and original author?

No. Recovery relies on data archived before deletion. It creates a new channel and replays available records with original metadata labels; it cannot impersonate original authors or restore Discord's deleted IDs and every live interaction state.

Does the website control my Discord server?

No. The website is static documentation and an illustrative showcase. It does not authenticate with Discord, query tickets, publish panels, or run bot commands.
